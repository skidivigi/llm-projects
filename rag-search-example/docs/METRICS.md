# Метрики поиска в RAG Search Lab

Заметка описывает показатели нашего стенда и основные обозначения из отчётов по поиску. Мы пока оцениваем **найденный контекст**, а не ответ, сгенерированный LLM.

## 1. Что именно оцениваем

В наборе 15 документов и 14 контрольных вопросов:

- у 12 вопросов есть ответ в документах;
- у 2 вопросов ответа нет: телефон поддержки VPN и стоимость обеда.

Документ разбивается на **чанки**. Один чанк сохраняется в Qdrant как **точка**: ID, embedding-вектор и payload с текстом и метаданными.

Один документ может дать несколько точек. Поэтому `top_k=2` возвращает до двух **чанков**, которые могут принадлежать одному документу.

Данные для проверки:

| Поле | Значение |
|---|---|
| `expected` | ID документов, нужных для ответа |
| `evidence` | Эталонные фрагменты текста с ответом: документ, цитата и символьные границы |
| `hits` | Чанки, реально попавшие в выдачу |
| `covered` | Для каждого эталонного фрагмента: покрыт ли он найденными чанками |

Для вопроса о сроках хранения prod и dev нужны два документа и два фрагмента: «Копии хранятся 30 дней» и «Копии хранятся 7 дней».

## 2. Метрика, score и параметр — разные вещи

| Что | Примеры | За что отвечает |
|---|---|---|
| **Метрика качества** | Recall, EvidenceRecall, Precision, MRR | Сравнивает выдачу с эталоном |
| **Оценка модели — score** | `dense_score`, `rerank_logit` | Определяет порядок или фильтрацию результатов |
| **Параметр поиска** | `top_k`, `candidate_k`, `threshold` | Управляет алгоритмом выдачи |
| **Параметр разбиения** | `size`, `overlap` | Определяет состав чанков |
| **Вариант выдачи** | `dense_topk`, `rerank_topk` | Обозначает, каким способом отобрали результаты |

Высокий score не доказывает, что фрагмент содержит ответ. Например, восстановление БД получило score выше инструкции о сроке хранения, хотя вопрос был именно о сроках.

## 3. Recall@k — R@k

**Какую долю всех нужных результатов нашли в первых k позициях?**

`Recall@k = число найденных нужных объектов / общее число нужных объектов`

Пример: нужны prod и dev. В top-2 пришли восстановление и prod:

`R@2 = 1 / 2 = 0.5`

Пришли prod и dev:

`R@2 = 2 / 2 = 1.0`

`@k` обозначает глубину выдачи, на которой считается показатель. Сам показатель может оценивать документы, чанки или другую размеченную единицу — это нужно уточнять в каждом отчёте.

Recall не учитывает лишние результаты и сам по себе не оценивает их порядок. Все нужные фрагменты можно найти вместе с большим количеством шума.

## 4. DocRecall — нашли ли нужные документы

**Нашли ли хотя бы один чанк каждого нужного документа?**

`DocRecall = число уникальных найденных нужных документов / число нужных документов`

В нашем коде найденные `doc_id` превращаются в множество. Два чанка одного документа засчитываются как один найденный документ.

Примеры:

- нужны prod и dev, вернулся только prod → `0.5`;
- нужны prod и dev, вернулись два чанка prod → всё ещё `0.5`;
- нужен prod, вернулось его вступление без срока хранения → `1.0`.

Последний пример показывает ограничение: **источник найден, но самого ответа в выдаче может не быть**.

В шаге 2 поле `recall_at_k` считалось по ID документов. После появления чанков тот же смысл выражает `doc_recall`.

## 5. EvidenceRecall — нашли ли текст с ответом

**Какую долю размеченных фрагментов ответа полностью покрывает найденный контекст?**

`EvidenceRecall = число полностью покрытых эталонных фрагментов / число эталонных фрагментов`

В нашей реализации:

1. Для найденных чанков берём символьные диапазоны `[start, end)`.
2. Объединяем соседние и перекрывающиеся диапазоны отдельно для каждого документа.
3. Проверяем, содержится ли каждый эталонный диапазон целиком внутри найденного покрытия.

Два соседних чанка вместе могут покрыть один эталон. Частичное покрытие эталонного фрагмента не засчитывается: результат по нему либо `true`, либо `false`.

Для вопроса про prod и dev:

| Что извлекли | DocRecall | EvidenceRecall |
|---|---:|---:|
| Вступления обоих документов, без сроков | 1.0 | 0.0 |
| Срок prod, документ dev не найден | 0.5 | 0.5 |
| Срок prod и вступление dev без срока | 1.0 | 0.5 |
| Оба срока | 1.0 | 1.0 |

Это **наша метрика строгого покрытия заданных отрывков**, а не универсальная оценка смысла ответа. Она не считает долю найденных слов, не проверяет генерацию LLM и не засчитывает альтернативное правильное объяснение, не предусмотренное разметкой.

Длинный эталонный отрывок может задавать более строгое требование, чем краткий ответ на вопрос. Результат зависит от того, насколько точно размечены минимально необходимые сведения.

## 6. Precision@k — P@k

**Какая доля первых k результатов релевантна?**

Для фиксированной глубины:

`P@k = число релевантных результатов в первых k позициях / k`

Пример: нужен один документ, а в top-2 пришли нужный и лишний:

- `R@2 = 1.0`: всё нужное нашли;
- `P@2 = 0.5`: половина выдачи лишняя.

Если после фильтрации вернулось меньше k результатов, соглашение важно:

- стандартный вариант P@k сохраняет знаменатель k;
- доля полезных среди **фактически возвращённых** делит на размер непустой выдачи. Это другой показатель.

Например, запросили k=2, вернули один полезный результат: P@2 с фиксированным знаменателем равен 0.5, а доля полезных среди возвращённых — 1.0.

**В текущих скриптах Precision не реализован.** Для добавления нужно определить релевантность именно чанков и обработку дублей. Нельзя автоматически считать любой чанк нужного документа полезным для ответа.

[Определения Precision и Recall: Stanford IR Book](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-unranked-retrieval-sets-1.html)

## 7. Hit@k

**Есть ли хотя бы один нужный результат среди первых k?**

Для одного вопроса: `1`, если есть; `0`, если нет. Среднее по вопросам показывает долю вопросов хотя бы с одним попаданием.

В top-2 пришли восстановление и prod. Для вопроса, которому нужны prod и dev:

- `Hit@2 = 1`: одно попадание есть;
- `DocRecall = 0.5`: второй нужный документ не нашли.

Поэтому Hit@k недостаточно для вопросов, требующих нескольких источников. В наших скриптах отдельно не выводится.

## 8. MRR@k — место первого нужного результата

Для одного вопроса считаем reciprocal rank:

`RR@k = 1 / позиция первого нужного результата`

Если нужного результата в первых k нет, значение равно 0. MRR@k — среднее RR@k по оцениваемым вопросам.

| Первое попадание | RR |
|---|---:|
| На первом месте | 1.0 |
| На втором | 0.5 |
| На третьем | 0.333… |
| За пределами k или отсутствует | 0.0 |

В вопросе про prod/dev до reranker первым стояло восстановление, вторым — prod: RR@2 по нужным документам равен 0.5. После reranker первым стал prod: RR@2 равен 1.0.

MRR не проверяет наличие всех нужных источников. Если первым стоит prod, а dev отсутствует, RR остаётся 1.0.

В шаге 2 `mrr_at_k` реализован по нужным **документам**. В отчётах шагов 3–4 MRR не выводится; там основное внимание уделено покрытию ответа.

## 9. nDCG@k

**Насколько хорошо упорядочены результаты с учётом степени релевантности?**

Нужна разметка уровней полезности, например: 0 — не подходит, 1 — частично полезно, 2 — прямо отвечает на вопрос. Полезный результат выше в списке получает больший вклад. Итог нормируется относительно идеального порядка.

Значение 1 означает идеальный порядок по выбранной разметке. Как правило, полезно для сравнения ранжирования, если результаты имеют разную степень полезности.

**В нашем стенде nDCG не реализован.** Наших списков expected и символьных evidence недостаточно для готовой градуированной разметки каждого кандидата.

[nDCG: документация scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html)

## 10. False accept rate — ложная выдача

**Как часто поиск возвращает что-либо на вопрос, для которого в наборе нет ответа?**

`false_accept_rate = число вопросов без ответа с непустой выдачей / число вопросов без ответа`

У нас два таких вопроса:

| Что произошло | Значение |
|---|---:|
| На оба вернули хотя бы один чанк | 1.0 |
| На один вернули, на другой — нет | 0.5 |
| Обе выдачи пустые | 0.0 |

Здесь оценивается **непустая выдача**, а не галлюцинация LLM. Модель генерации пока не подключена. Это также не доля всех нерелевантных чанков во всех выдачах.

Если прогоняется только q11, значение равно `null`: в этом прогоне нет вопросов без ответа. Для q13 одного достаточно, чтобы посчитать показатель: непустая выдача даст 1.0.

Возврат пустой выдачи по всем вопросам даст хорошее значение false_accept_rate, но провалит Recall на вопросах с ответом. Эти показатели нужно читать вместе.

## 11. Шум и дубли

### mean_noise — среднее количество лишних результатов

В шаге 2 считали количество возвращённых документов, которых нет в expected для данного вопроса. Затем усредняли по **всем 14 вопросам**, включая вопросы без ответа.

`mean_noise = сумма количества лишних результатов / число вопросов`

Например, 3 лишних результата суммарно на 14 вопросов дают `3 / 14 ≈ 0.2143`. Это среднее **количество**, а не доля; оно может быть больше 1.

При переходе к чанкам такой подход не замечает ненужные части нужного документа. Поэтому в шагах 3–4 mean_noise не выводится; вместо него используем покрытие evidence и показатели объёма и дублей.

### mean_duplicate_share — повторное покрытие исходного текста

Для одного вопроса:

`duplicate_share = (суммарная длина чанков − длина уникального покрытия) / суммарная длина чанков`

Диапазоны объединяются отдельно по документам. Считаются **символы**, а не токены. Например, два чанка по 100 символов перекрываются на 40: суммарно получили 200 символов, уникальных 160, доля дублей — `0.2`.

`mean_duplicate_share` — среднее этой доли по всем вопросам. Пустая выдача даёт 0.

Это не поиск смысловых повторов между разными документами. Два неперекрывающихся чанка одного документа могут иметь duplicate_share=0. Сам overlap не гарантирует дубли в выдаче: перекрывающиеся чанки могут не попасть в неё одновременно.

## 12. Объём и время

| Поле | Что измеряем | Ограничение |
|---|---|---|
| `context_tokens` | Сумма body_tokens выбранных чанков для вопроса | Не точный размер будущего prompt LLM |
| `mean_context_tokens` | Среднее context_tokens по всем вопросам, включая пустые выдачи | Разные размеры чанков при одном k дают разный объём текста |
| `embedding_ms` | Получение embedding вопроса с ожиданием GPU | Загрузка модели исключена |
| `search_ms` | Время клиентского запроса к Qdrant | Включает HTTP-обмен и обработку клиента, не только работу сервера |
| `rerank_ms` | Проверка длины пар, токенизация, вычисление logits и сортировка | Загрузка/скачивание модели исключены |
| `mean_rerank_ms` | Среднее дополнительное время rerank по вопросам | Маленький прогон не является производственным бенчмарком |
| `chunks_count` | Количество чанков/точек в коллекции | Это размер индекса, не метрика качества |

Для оценки производительности позже нужны повторные замеры и распределение задержек, например p50/p95. В текущем опыте смотрим только диагностические значения.

## 13. Как усредняются наши показатели

DocRecall, EvidenceRecall и MRR шага 2 усредняются **по вопросам с ответом**. Каждый вопрос имеет одинаковый вес — это macro-average.

Например, 11 вопросов получили Recall=1, а вопрос с двумя источниками — 0.5:

`среднее = (11 × 1 + 0.5) / 12 ≈ 0.9583`

Это не то же самое, что делить общее число найденных эталонов на их общее количество: такой micro-average даст другие веса вопросам с несколькими эталонами.

Для вопросов с `expected=[]` DocRecall и EvidenceRecall равны `None`/`null`, а не 0. Они исключаются из этих средних и проверяются через false_accept_rate.

Значение 0.875 означает **среднюю долю покрытия**, а не обязательно «87.5% вопросов полностью отвечены». Для доли полностью покрытых вопросов потребовалась бы отдельная метрика.

## 14. Scores: dense_score и rerank_logit

### Dense score

Dense-поиск сравнивает embedding-вектор вопроса с векторами чанков. В нашем стенде используется cosine similarity: большее значение означает более близкие векторы; теоретический диапазон — от −1 до 1.

`dense_score=0.85` не означает «85% вероятности правильного ответа». Порог отсеивает результаты, но не меняет их порядок. Если нерелевантный чанк стоит выше полезного, повышение порога может раньше убрать полезный.

BM25 — другая первая стадия поиска: по совпадениям слов с учётом их редкости и длины документа. Мы его пока не добавляли. BM25 score также не является процентом правильности и имеет свою шкалу.

### Rerank logit

Reranker получает одновременно вопрос и текст одного кандидата. В нашей реализации большее значение rerank_logit означает более высокий порядок. Значение может быть отрицательным или больше 1; его нельзя сравнивать с cosine score.

Наблюдения на наших вопросах:

| Пример | Лучшие logits |
|---|---|
| Сроки prod/dev — ответ есть | 2.47 и 2.00 |
| Телефон поддержки — ответа нет | −8.67 и −8.80 |
| Стоимость обеда — ответа нет | −10.02 и −10.09 |

Это даёт гипотезу для отдельного порога reranker, но не универсальную границу. Отрицательная оценка сама по себе не доказывает бесполезность. Проверяем сохранение нужных ответов и отказы на новых вопросах.

## 15. Названия строк в сравнении reranker

**Это варианты выдачи, а не метрики.** Метрики находятся в столбцах таблицы.

| Строка | Состав выдачи |
|---|---|
| `candidates` | Все 10 кандидатов исходного dense-поиска без порога |
| `dense_topk` | Первые 2 кандидата в исходном порядке, без порога |
| `rerank_topk` | Лучшие 2 после пересортировки тех же кандидатов, без порога |
| `dense_reference_085` | До 2 исходных результатов с dense score ≥ 0.85; справочная старая настройка |

Чистое сравнение эффекта сортировки: **dense_topk против rerank_topk**. Сравнение с dense_reference_085 также меняет фильтрацию, поэтому весь прирост нельзя приписывать reranker.

Если кандидаты покрывают ответ, а финальная выдача его теряет, проблема в отборе, порядке или ограничении k. Если ответа нет уже среди кандидатов, reranker его добавить не сможет. Наличие всех эталонов в 10 кандидатах также не гарантирует, что они поместятся в двух финальных чанках.

В полном прогоне без порогов false_accept_rate=1 ожидаема: для обоих вопросов без ответа принудительно выбираются лучшие чанки. Для отказа нужно отдельное проверенное правило.

## 16. Наш результат после reranker

Чанки 128, overlap=0, кандидатов 10, финальный k=2:

| Выдача | DocRecall | EvidenceRecall | Ложная выдача | Средний контекст |
|---|---:|---:|---:|---:|
| dense_topk | 0.958 | 0.958 | 1.000 | 169.0 токена |
| rerank_topk | 1.000 | 1.000 | 1.000 | 220.1 токена |
| dense_reference_085 | 0.875 | 0.875 | 0.000 | 133.3 токена |

Среднее дополнительное время rerank в этом прогоне — 44.8 мс.

- Снятие dense-порога вернуло q09 про отпуск: полезный ответ прежде отсеивался.
- Reranker исправил q11: вместо восстановления и prod выбрал prod и dev.
- Покрытие остальных вопросов с ответом сохранилось.
- Вопросы без ответа пока возвращают фрагменты: отказ не настроен.

EvidenceRecall=1 означает полное покрытие размеченных текстов на **12 вопросах с ответом**. Это не доказательство отсутствия шума, правильности генерации или качества на любых новых вопросах.

## 17. Быстрая памятка

| Вопрос при чтении отчёта | На что смотреть |
|---|---|
| Нашли ли нужный источник? | DocRecall |
| Попал ли сам текст ответа в контекст? | EvidenceRecall |
| Много ли лишних результатов? | Precision или определённый показатель шума |
| Высоко ли стоит первое попадание? | MRR; для хотя бы одного попадания — Hit@k |
| Хорошо ли упорядочены результаты разной полезности? | nDCG с соответствующей разметкой |
| Отказываемся ли при отсутствии ответа? | false_accept_rate вместе с Recall |
| Не заполняем ли контекст повторениями? | mean_duplicate_share |
| Сколько текста передадим дальше? | mean_context_tokens |
| Сколько стоит обработка? | embedding_ms, search_ms, mean_rerank_ms |

При сравнении фиксируем документы, вопросы, разбиение, кандидатный набор, финальный k и правила фильтрации. Изменяем один фактор. Новые вопросы используем для проверки того, что настройка не подогнана только под учебный набор.

- Формулы и соглашения нашего стенда: `lab_common.py` — Recall, RR и шум шага 2; `search.py` — усреднение шага 2; `chunk_lab.py` — покрытие evidence, дубли и усреднение; `rerank_lab.py` — варианты выдачи и время rerank.
- Precision, Hit@k и nDCG приведены для понимания распространённых отчётов; текущие скрипты их отдельно не рассчитывают.
